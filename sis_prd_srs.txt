SIMPLEIN SCHOOL
Product Requirements & Software Requirements Specification
Team Preparation Guide
Purpose of This Guide
This guide is the working instruction for the team member responsible for preparing the SimpleIn School Product Requirements & Software Requirements Specification. It defines what must be researched, written, validated and delivered in each section. The completed PRD/SRS will act as the primary requirements baseline for product design, development, QA, UAT, implementation and the remaining SimpleIn School documentation packages.
Completion Principles
Document actual product requirements; do not invent features merely to make the document look complete.
Separate confirmed requirements from assumptions, proposals and future ideas.
Every material functional requirement must be uniquely identifiable and testable.
Use clear, unambiguous language. Prefer 'The system shall...' for mandatory requirements.
Validate school workflows with relevant stakeholders before finalizing requirements.
Avoid prescribing implementation technology unless the requirement genuinely depends on it.
Keep detailed database schema, API specifications, test cases and implementation SOPs in their respective downstream documents.
Every requirement should be traceable to a module, business need and later test/UAT evidence.
Any unresolved point must be recorded rather than silently guessed.
Required Output
Deliver one controlled document titled: SIMPLEIN SCHOOL — Product Requirements & Software Requirements Specification (PRD & SRS). It should be concise in narrative sections but detailed enough in the requirements sections to serve as a development and testing baseline.

6. Stakeholders & User Types
Purpose: Identify people who influence, operate, approve or consume the product.
Include stakeholder register and user types.
For each user type, document: responsibilities, primary tasks, information accessed, decisions made and expected system interaction.
Do not finalize roles without validating them against the actual school operating model.
7. Product Scope
Purpose: Define the exact boundary of the product version being specified.
Create three lists:
In Scope — functionality included in the specified release/product baseline.
Out of Scope — functionality explicitly excluded.
Future Scope — potential later functionality that is not part of the current baseline.
Every major module or capability should appear in one of these categories. Avoid vague scope statements.

11. Business Rules
Purpose: Capture rules that govern school operations and system behavior independently of UI implementation.
Use ID format BR-[MODULE]-[NUMBER].
For each rule include:

Applicable module/process

Example pattern: 'Only authorized users assigned the relevant responsibility may modify attendance for a class.' Replace examples with verified school rules.
12. Roles & Access Requirements
Purpose: Define high-level authorization expectations.
Include:
List of system roles
Responsibilities of each role
Modules each role can access
High-level actions: View/Create/Edit/Delete/Approve/Export where applicable
Scope limitations, such as own class, own child or own department
This is the requirements-level access model. Detailed permission IDs and technical RBAC implementation belong in the technical/security documentation.
13. Non-Functional Requirements
Purpose: Define how well the system must operate.
Cover at least:
Performance — response time, report generation, concurrency targets where measurable.
Availability — uptime target and maintenance expectations.
Scalability — schools, users, students, transactions and document growth.
Security — authentication, authorization, encryption, session security and auditability.
Usability — navigation, responsive behavior, accessibility and error clarity.
Reliability — failure handling, consistency and recovery expectations.
Compatibility — supported browsers, devices and operating systems.
Maintainability — logging, monitoring, configuration and supportability.
Use measurable targets where the business has actually approved them. Do not invent numerical SLAs.

16. Reporting Requirements
Purpose: Define reports and operational information required by users.
Include academic, attendance, financial, administrative and other reports only when required by the actual product scope.
17. Acceptance Requirements
Purpose: Define how the requirements will be considered successfully implemented.
Include:
Requirement-level acceptance criteria

18. Assumptions, Constraints & Dependencies
Purpose: Keep conditions and limitations visible so the team does not silently make decisions.
Assumptions:
Document statements believed to be true but not fully controlled by the project.
Constraints:
Document limitations related to budget, resources, timeline, infrastructure, third-party services or customer environment.
Dependencies:
Document internal teams, customer inputs, external services, hardware, APIs or other prerequisites required for the product.
Every significant item should have an owner and status where practical.

Purpose: Connect business requirements to design, development, testing and UAT.
At initial approval, downstream references may be marked TBD. The matrix must be maintained as development and testing progress.

Team Preparation Workflow
Collect product inputs: existing SimpleIn School plans, module lists, school requirements, stakeholder notes and known constraints.
Interview or consult relevant business/school stakeholders for actual workflows.
Build the stakeholder, user and module catalogues.
Document current and desired business processes.
Draft scope before writing detailed requirements.
Write functional requirements using unique IDs and acceptance criteria.
Document business rules and role/access expectations.
Define non-functional, data, integration and reporting requirements.
Review requirements with the Technical Lead for feasibility and ambiguity.
Review requirements with the product/business owner for completeness and scope.
Resolve open questions or explicitly record them as unresolved rather than guessing.
Complete the traceability matrix.
Submit the controlled draft for approval.

What This Document Must NOT Contain in Detail
Detailed database table definitions and SQL schema — Document 2.
Detailed API endpoint specifications — Document 2.
Detailed test cases and test execution results — Document 3.
Commercial pricing, quotations and contract clauses — Document 4.
Detailed school onboarding SOPs and training procedures — Document 5.
Unapproved feature ideas presented as committed requirements.
