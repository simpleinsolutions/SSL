## 2. Prerequisites & Environment Variables

### 2.1 Required Environment Secrets

| Variable Name | Required | Description | Example / Format |
| :--- | :---: | :--- | :--- |
| `NEXT_PUBLIC_SUPABASE_URL` | Yes | Supabase Project URL | `https://xyzproject.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Yes | Public Anonymous Client Key | `eyJhbGciOiJIUzI1NiIsInR5cCI6...` |
| `SUPABASE_SERVICE_ROLE_KEY` | Yes | High-privilege Backend Key (Never leak to client) | `eyJhbGciOiJIUzI1NiIsInR5cCI6...` |
| `ONBOARDING_SECRET` | Yes | Secret passphrase for school tenant provisioning | 64+ char random hex string |
| `NODE_ENV` | Yes | Execution environment | `production` |

> [!WARNING]
> `SUPABASE_SERVICE_ROLE_KEY` and `ONBOARDING_SECRET` must **never** be prefixed with `NEXT_PUBLIC_` or bundled into browser code. They are strictly server-side environment secrets.

## 3. Database Migration Deployment

All 27 PostgreSQL migrations in `supabase/migrations/` must be applied in strict alphabetical/timestamp order.

### 3.1 Applying Migrations via Supabase CLI

```bash
# 1. Install Supabase CLI (if not already installed)
npm install -g supabase

# 2. Login to your Supabase organization
supabase login

# 3. Link your local repository to the production project
supabase link --project-ref <your-supabase-project-id>

# 4. Push and execute all migrations against the remote database
supabase db push
```

### 3.2 Verifying Migration Integrity

Run the following query in the Supabase SQL Editor to verify all 27 migrations are applied:

```sql
SELECT version, name FROM supabase_migrations.schema_migrations ORDER BY version;
```

Confirm that the final migration `20260401000026_final_rls_tightening.sql` is present and active.

## 4. Supabase Storage Configuration

The system requires 3 private storage buckets for academic files:

```sql
-- Create private storage buckets
INSERT INTO storage.buckets (id, name, public)
VALUES 
  ('homework', 'homework', false),
  ('receipts', 'receipts', false),
  ('report-cards', 'report-cards', false)
ON CONFLICT (id) DO UPDATE SET public = false;
```

Verify that all 3 buckets have `public = false`. All downloads must use signed URLs generated by `lib/services/storage.ts`.

## 5. Deploying to Vercel (Recommended)

### 5.1 Project Setup
1. Push your clean Git repository to GitHub: `git push origin main`.
2. Open the [Vercel Dashboard](https://vercel.com/) and click **Add New Project**.
3. Import the `simpleinsolutions/SSL` repository.
4. Framework Preset: **Next.js**.
5. Root Directory: `./` (leave default).

### 5.2 Build & Development Settings
- **Build Command:** `npm run build`
- **Output Directory:** `.next`
- **Install Command:** `npm install`

### 5.3 Configure Environment Variables
In the Vercel Project Settings under **Environment Variables**, add:
- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- `ONBOARDING_SECRET`
- `NODE_ENV = production`

### 5.4 Deploy
Click **Deploy**. Vercel will execute `npm run build`, generating serverless functions for all dynamic route handlers and optimizing static pages.

## 6. Docker Container Deployment (Alternative Self-Hosted)

For schools requiring on-premises or dedicated cloud deployments, use the following production `Dockerfile`:

```dockerfile
FROM node:20-alpine AS base

# Install dependencies only when needed
FROM base AS deps
RUN apk add --no-cache libc6-compat
WORKDIR /app
COPY package*.json ./
RUN npm ci

# Rebuild the source code only when needed
FROM base AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ENV NEXT_TELEMETRY_DISABLED 1
ENV NODE_ENV production
RUN npm run build

# Production image, copy all the files and run next
FROM base AS runner
WORKDIR /app
ENV NODE_ENV production
ENV NEXT_TELEMETRY_DISABLED 1

RUN addgroup --system --gid 1001 nodejs
RUN adduser --system --uid 1001 nextjs

COPY --from=builder /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static

USER nextjs
EXPOSE 3000
ENV PORT 3000
ENV HOSTNAME "0.0.0.0"

CMD ["node", "server.js"]
```

## 7. Zero-Downtime Deployment & Health Checks

### 7.1 Health Check Endpoint
The application includes an automated health check route at:
`GET /api/v1/health`

**Expected Response (HTTP 200 OK):**
```json
{
  "status": "healthy",
  "service": "simplin-school-erp",
  "version": "0.1.0",
  "database": "connected",
  "timestamp": "2026-10-29T14:45:00.000Z"
}
```

Configure your load balancer or uptime monitor (e.g., UptimeRobot, Datadog, AWS Route 53) to poll `/api/v1/health` every 60 seconds.

## 8. Post-Deployment Verification Checklist

Once the production deployment completes, perform the following verification protocol:

- [ ] **Health Check:** `curl -i https://your-domain.com/api/v1/health` returns `200 OK`.
- [ ] **Landing Page:** Visit `https://your-domain.com/` and confirm that 3D visuals, floating emblems, and portal gateways render without visual artifacts.
- [ ] **Login Portal:** Navigate to `https://your-domain.com/login` and verify that the 3D role tabs, recessed inputs, and demo credential fills respond smoothly.
- [ ] **Admin Authentication:** Authenticate as `admin@delhi-public.demo` and verify that `/admin` loads with 4 3D KPI stat cards and 12 quick action cards.
- [ ] **Teacher Portal:** Authenticate as `teacher@delhi-public.demo` and verify `/teacher` displays assigned classrooms and roll-call triggers.
- [ ] **Parent Portal:** Authenticate as `parent@delhi-public.demo` and verify `/parent` renders multi-child tabs and fee records.
- [ ] **Student Portal:** Authenticate as `student@delhi-public.demo` and verify `/student` renders today's timetable and homework tasks.
- [ ] **SSL / TLS:** Verify that HTTPS is enforced with HSTS headers enabled.
- [ ] **Cookie Flags:** Verify that session cookies carry `HttpOnly`, `SameSite=Lax`, and `Secure` attributes.
- [ ] **Private Storage:** Attempt direct unauthenticated HTTP GET on a bucket path; verify that `400/403 Access Denied` is returned.

## 9. Backup, Disaster Recovery & Maintenance

1. **Automated Daily Backups:** Ensure Supabase point-in-time recovery (PITR) is enabled with a minimum retention period of 7 days.
2. **Offsite Snapshotting:** Configure a scheduled GitHub Action or cron worker to export encrypted database dumps:
   ```bash
   pg_dump "postgresql://postgres:[PASSWORD]@[HOST]:5432/postgres" --clean --if-exists -F c -b -v -f "backup-$(date +%Y%m%d).dump"
   ```
3. **Emergency Rollover:** In the event of catastrophic primary cluster degradation, update DNS records to point to your hot standby cluster and re-apply secret keys.
