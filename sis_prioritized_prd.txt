1. Product Goal
Build one secure, reliable company operating system that connects SIMPLEIN’s business operations with the work performed by every employee. Authorized users must be able to trace a piece of work from assignment through progress, submission, review, correction and acceptance, and connect it to a project, customer or business outcome when relevant.
The software must be useful for a company with fewer than ten people, where employees may take on work outside their usual roles. The system must support flexible assignments without confusing job roles, task-specific access permissions, ownership, contributors and reviewers.

5. Core Work Lifecycle
Co-founder decision: some task categories may not need formal review. Define which categories require review and who is authorized to accept them. Do not make a submission automatically equivalent to acceptance.
6. Role, Assignment and Permission Rules
Every user has a base role or permission profile; the exact list and matrix must be approved.
Each task has one accountable owner; additional contributors are explicitly recorded.
An employee may be assigned cross-role work without changing their permanent role.
Task assignment alone must not grant broad access to unrelated confidential records.
Reviewers must be authorized for the task category and, where appropriate, must not approve their own work.
Sensitive actions such as user administration, permission changes, and financial corrections require explicit permissions and audit records.
Permissions are enforced server-side for pages, APIs, data exports and file downloads.
Deactivated users cannot continue using sessions or accessing protected data.
7. Employee Contribution Reporting Rules
The system should first produce factual, traceable records. It should not automatically equate raw task counts, hours, or message volume with performance.
Timesheets and weighted employee scores are not assumed to be mandatory. Decide separately whether they are needed, how they will be used, and how employees can see or challenge inaccurate records.
8. Data Model: Core Entities
This is a conceptual entity list, not the final database schema. Field-level definitions, cardinalities, deletion behavior, retention, uniqueness and indexes must be documented before migrations are finalized.
9. Definition of 'Perfectly Working'
Absolute perfection cannot be guaranteed. The engineering target is verifiable correctness: every approved feature has explicit expected behavior, tests, security checks, and observable acceptance evidence.
10. Testing Strategy and Release Gates
Unit tests: domain rules, validators, calculations, permissions and state transitions.
Integration tests: database writes/reads, transactions, file authorization, authentication and API behavior.
End-to-end tests: real user workflows from sign-in through task completion, review and reporting.
Negative security tests: direct API access, ID tampering, cross-user access, role escalation and unauthorized file access.
Regression tests: each repaired bug becomes a repeatable test where practical.
Data tests: duplicates, missing references, invalid transitions, concurrent updates and financial edge cases.
Operational tests: backup restore, environment configuration, deployment and rollback.
User acceptance testing: co-founder/representative users validate workflows against written acceptance criteria.
Release gate: do not call a feature complete because the UI renders or a manual happy-path demo works. Require the agreed acceptance criteria, test evidence, permission checks, data-persistence verification, and regression checks.
11. Non-Functional Requirements to Quantify
Before launch, co-founders and the engineering owner should set measurable targets for:
Expected concurrent users and data/file volumes.
Response-time targets for common actions and report queries.
Backup frequency, retention period, and acceptable recovery time/data loss.
File type and size limits, retention/deletion, and access policy.
Availability expectations and maintenance windows.
Supported browsers and minimum viewport sizes.
Audit-log retention and who can access/export logs.
Privacy policy for employee work records and correction of inaccurate records.

13. Proposed MVP Exit Checklist
Co-founders have signed off on the scope, role-permission matrix, task lifecycle and review rules.
Authentication, account lifecycle, server-side authorization and audit controls are verified.
Employees can be assigned internal or customer-linked work, including cross-role work, without privilege escalation.
Task progress, blockers, submissions, reviews, corrections and acceptance are persisted and auditable.
Employee contribution history records owners, collaborators and relevant evidence.
Core customer, lead, contact, activity, requirement and business records work and link to delivery records.
Financial features follow approved business rules and have edge-case tests.
Dashboards/reports reconcile to underlying records and enforce visibility rules.
Critical automated tests, type checks, lint, migrations and production build pass.
Backup restoration, release/rollback procedures, and user acceptance tests have been completed.
Open defects are triaged; no unresolved critical security or data-integrity defect is accepted for release.

15. Final Product Definition
SIMPLEIN is a company-wide business and work management platform. It combines customer/business operations with employee assignments, contributions, deliverables, reviews, audit history and management reporting. The distinguishing requirement is that the company can trace meaningful work from assignment to verified outcome while maintaining appropriate permissions and a fair, transparent record of contributions.
This PRD is a prioritized working baseline for co-founder alignment. Once approved, it should be expanded into implementation-level specifications before coding begins. Actual correctness must be demonstrated through tests and acceptance evidence; it cannot be guaranteed by the document alone.

State | Entry conditions | Required behavior / exit
Assigned | Task has owner, expected result and applicable priority/deadline. | Owner and contributors can see permitted task details; assignment event is recorded.
In progress | Owner starts work or records progress. | Updates and blockers are timestamped; status changes are validated.
Submitted for review | Required deliverable/evidence and completion notes are supplied. | Submission is versioned and preserved; required review is created.
Under review | An authorized reviewer takes the item. | Reviewer can accept or return it against the applicable criteria; decision is recorded.
Returned for correction | Reviewer provides actionable reason/comments. | Work reopens for correction; previous submission and review history remain intact.
Accepted | Authorized reviewer confirms criteria are satisfied, or configured task policy permits acceptance. | Acceptance decision, reviewer, timestamp and criteria outcome are recorded.
Closed | Closure conditions are met. | Item is finalized; reopening is permission-controlled and auditable.
Dimension | Possible evidence | Interpretation caution
Delivery | Accepted deliverables, due dates, completed milestones. | Consider task complexity, dependencies and approved deadline changes.
Quality | Review outcomes, defects, corrections and acceptance criteria. | Compare similar work types; a correction can be part of a healthy review process.
Reliability | Updates, response to blockers, commitments and delivery patterns. | Record blockers and reassignment decisions rather than blaming the assignee by default.
Collaboration | Recorded contributions to shared work and handoffs. | Avoid assigning all credit to a single task owner.
Impact | Relationship to project/customer outcomes and agreed objectives. | Do not claim causality where the data only shows association.

Quality area | Minimum acceptance expectation
Functional correctness | Each requirement has positive, negative, boundary and failure-path tests where applicable.
Persistence | Create/update/reload behavior is verified against the database; state does not rely only on client memory.
Authorization | Allowed and denied actions are tested at the server/API and file-access layers.
Data integrity | Relationships, uniqueness, transactions and financial calculations are validated.
Workflow correctness | Invalid transitions are rejected; required fields and approvals cannot be bypassed.
History and audit | Important events and corrections remain traceable; prior submissions are not silently overwritten.
Usability | Loading, empty, validation, success, error and recovery states are implemented; layouts work at agreed screen sizes.
Reliability | Expected failure modes are handled without corrupting data; backup restoration is tested.
Maintainability | Type checks, lint, automated tests, migrations and production build are repeatable.
Release safety | Critical defects are fixed or explicitly block release; known limitations are documented; rollback steps are available.
Decision | Why it matters | Recommended next action
Role-permission matrix | Controls access to all business and employee records. | List every role and actions: view/create/edit/assign/review/approve/export/delete.
Work review policy | Determines when work can be accepted or closed. | Define task categories, reviewer eligibility and acceptance criteria.
Daily summaries vs task-driven history | Affects data-entry burden and reporting completeness. | Start with task-driven history and optional daily summaries unless a specific policy requires daily reporting.
Timesheets | Affects workflow, privacy and reporting. | Keep out of MVP unless there is a concrete operational need.
Financial rules | Avoids inconsistent invoices and payment states. | Approve numbering, tax/totals, partial payments, refunds/credits and corrections.
File handling | Affects security, cost, and retention. | Choose private storage and define version, deletion and size/type rules.
Technology and hosting | Affects build, deployment, backups and ongoing cost. | Confirm stack, authentication, database, storage and deployment before implementation.
Performance/availability targets | Defines meaningful launch readiness. | Agree realistic measurable thresholds based on expected usage.
